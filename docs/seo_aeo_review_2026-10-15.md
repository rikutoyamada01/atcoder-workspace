**クロール・正規化・配信設定**

当面は既存の `presentation.html` を製品の正規URLとして維持し、リンクとメタ情報をそろえるのが小さい変更。トップがインデックスされていることだけを根拠に、直ちにURLを移行する必要はない。

- `pages/index.html:5` の0秒meta refreshは、Googleが恒久転送として扱う有効な方式。既存監査の「SEO/AEOに弱い」という警告は一般化しすぎている。[Googleの転送仕様](https://developers.google.com/search/docs/crawling-indexing/301-redirects)
- 記事4件、記事一覧などに自己参照canonicalを追加する。ただしcanonicalの欠落は、それだけでインデックス不可になる条件ではない。
- 記事末に本文に関連する記事2件・記事一覧・製品紹介のリンクを置く。GoogleはJSで生成したリンクも処理できるが、初期HTMLのリンクはJSを実行しない閲覧環境でも利用できる。大規模なフレームワーク変更は不要。
- 重要な製品ページと記事1〜2件は、GSCのライブテストで取得と表示を確認し、必要に応じて登録リクエストする。今回取得したURL検査結果はライブテストの代用にはならない。
- サイトマップは既に送信済み。処理待ちを「正常に取得済み」とは扱わず、最終取得日時・エラー・各ページのクロールを追う。同じサイトマップを何度も再送する施策は優先しない。
- 現在の転送元トップを、正規化方針を変えずにサイトマップへ足す必要はない。将来トップに製品本文を置く場合は、旧ページの転送・canonical・内部リンク・サイトマップをまとめて切り替える。

`pages/presentation.html:17` のOGP画像 `/atcoder-workspace/icons/icon128.png` は公開HTTP取得で404。配信対象は `.github/workflows/deploy-pages.yml:39` の `pages/` のみで、該当画像がない。`pages/assets/` 等に配信用画像を置き、公開URLを修正する。これはまず共有表示の改善であり、404画像だけで検索順位低下を証明するものではない。

`/atcoder-workspace/robots.txt` は200だが、ホスト直下 `/robots.txt` は404。robots.txtはホスト直下が必要なので、現状のファイル内のサイトマップ宣言はrobots経由の発見には使われない。ただし、404だから検索を拒否しているわけではない。GSCにサイトマップを直接送信済みなので、この点だけを理由にドメイン移行する必要はない。[robots.txtの配置要件](https://developers.google.com/crawling/docs/robots-txt/create-robots-txt)

`scripts/seo-pdca-audit.js:350` はファイルのmtimeをサイトマップの更新日にする。チェックアウトやコピーで変わるため、実質的な内容更新日と一致しないことがある。確かな更新日を使うか、不確かな間は任意のlastmodを省く。[サイトマップのlastmod仕様](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)

**SEOとAEO・GEOのコンテンツ方針**

今ある4記事の修正後は、製品に近い検索意図を優先する。以下は需要量を取得したキーワード一覧ではなく、ユーザーの用途から立てた仮説。GSCで実際の表示が増えたら優先度を調整する。

| 想定される意図 | 既存ページに追加する内容・記事候補 | 製品につながる説明 |
| --- | --- | --- |
| AtCoder Workspaceとは／導入方法 | 導入ガイド、対応範囲、初回操作の実画面 | ストアへの直接リンクと練習問題の操作手順 |
| AtCoder 問題文 エディタ 横／画面分割 | 分割表示・幅変更・元の表示への戻し方 | 実画面で機能と制約を見せる |
| AtCoder サンプル 自動テスト／出力比較 | WAになるサンプル→Diff→修正→再実行の例 | サンプル通過と本提出のACは別と説明 |
| AtCoder コード 自動保存／消えた | 保存タイミング、保存先、端末変更・削除時の扱い | 復元できる範囲を具体的に答える |
| TLE／整数除算 | 既存ツール・記事の修正、条件・反例・検証結果 | 学習内容とサンプルテストの使い方を自然につなぐ |

FAQには、対応ブラウザ、ログイン・ネット接続の必要性、テストの実行場所、保存データの扱い、競技中の利用条件の確認先、不具合時の報告先を追加する。各回答は結論→条件→手順・出典の順にすると読者が判断しやすい。これはAI向けの特別な文字数・書式の要求ではない。

作者自身の操作画面、再現例、確認した製品バージョン、問題が起きた条件など、他サイトの一般論の再要約では得られない情報を増やす。記事の著者・プロフィール・公開日・実際の更新日・参照資料も表示する。

Googleは現行ガイドで、AEO・GEOも検索体験の最適化としてSEOの基本に沿うこと、独自の経験に基づく有用な情報を重視することを説明している。AI用の細切れ記事やキーワード違いの大量ページを作る施策は不要。[Googleの生成AI検索向け公式ガイド](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)

**計測と既存監査の改善**

既存の `npm run seo:audit` は24件の警告を返した。ただし、タグの存在・JSON構文を中心とした数なので、SEOの点数や重要度を示す数字としては使わない。製品ページは監査上OKでも、OGP画像404と導入リンク欠落が残っている。

`scripts/seo-pdca-audit.js:250`〜`:260` は約8日・検索語×ページ・最大50行・表示20以上かつCTR3%未満という固定条件。初期サイトでは、サイト合計とページ別の28日データ、URL検査、サイトマップ取得状態を先に見る方が実用的。検索語を含む取得結果だけからサイト合計を計算しない。

改善後の確認順は次のとおり。

1. 主要URLをGoogleが認識し、サイトマップを取得したか。製品ページと重要記事の最終クロール・canonicalを確認する。
2. 指名検索と、用途に関する検索で表示が発生するか。母数が小さい間はCTRや平均順位の変動に反応しすぎない。
3. 自然検索で入った訪問からストアへのクリックが発生するか。サイトで計測するなら、ストアへの遷移と実際のインストールを別の指標として扱う。
4. ストア側の取得可能な訪問・インストール実績と合わせて評価する。サイトのリンククリックだけでインストール増加とは結論しない。
5. Google生成AI検索については、GSCの「Search generative AI」設定で除外されていないかを確認し、利用可能なら生成AIパフォーマンスレポートの表示回数を追う。今回、その設定やAI実績は取得していない。

生成AIパフォーマンスレポートはAI Overviews・AI Modeの表示回数をページ・国・日付・端末などで確認するもので、表示が少ないとレポート自体が出ない場合がある。未表示だけで対象外や引用ゼロと断定しない。[レポート公式ヘルプ](https://support.google.com/webmasters/answer/16984139)、[掲載設定の公式ヘルプ](https://support.google.com/webmasters/answer/16908024)

まず導入CTA・記事訂正・画像404を直し、重要URLの取得を確認する。その後、28日単位で検索実績と導入への遷移を比較し、次の記事やタイトルの調整を決める。既存の静的HTMLと監査スクリプトの改善で進められ、新しいフレームワークや有料SEO基盤を先に導入する必要はない。

今回未計測なのはCore Web Vitals、訪問者の離脱・導入率、ストアのインストール数、Google生成AIレポート、他のAIサービスでの引用状況。これらが悪い／改善したという判定はしていない。
